# DECISIONS — 設計判断とその根拠

設計判断を変えた場合は、このファイルに理由ごと追記すること。

---

## D-001: 圧縮率はコミュニティ DB ではなくローカル実測で出す

**判断**: ネットワークに接続せず、対象マシンの実データを読んで測る。

**理由**:
- 通信ゼロは信頼の担保になる（無署名 EXE を配る以上、通信しないことが説明できるのは大きい）
- コミュニティ DB は同名タイトルでもバージョン・DLC・言語で構成が変わる
- 実測なら「このマシンのこのインストール」に対する答えが出る

**代償**: スキャンに時間がかかる。64MB のサンプリングで数秒〜十数秒。

---

## D-002: 圧縮率の測定は 32 KiB チャンク単位で行う

**判断**: サンプルを 32 KiB ごとに切り、個別に圧縮して合計する。

**理由**: WOF の LZX は 32 KiB チャンク単位で独立に圧縮するため、実効参照窓は 32 KiB しかない。

**実測による裏付け**（`docs/RESEARCH.md` §3）:
ファイル全体を 1 ストリームとして LZMA 圧縮すると、実測 LZX より **9〜13 pt 過大**に良い数字が出る。
一方 zlib（参照窓が元々 32 KB）はチャンク有無でほぼ変わらない。
この非対称性が、乖離の原因が参照窓サイズであることを直接示している。

---

## D-003: Brotli(q=9, window=15) を LZX の代理に使う。補正係数は 1.0

**判断**: `ChunkedBrotliProbe` の `calibration = 1.0`（補正なし）。

**実測による裏付け**（`docs/RESEARCH.md` §2）:
実ゲーム4種で最小二乗の補正係数は **k = 1.0001**。平均絶対誤差 2.05 pt / 最大 3.1 pt。
zlib（2.18 pt）や LZMA（2.80 pt）より Brotli が最も当たる。

**再検討の条件**: 標本が 4 プロファイルしかない。プロファイルを増やして誤差が偏るようなら再校正する。

**2026-07-30 追記**: 上の誤差 2.05pt は等質プロファイルに対する値で、
実タイトルの異種混合フォルダには一般化しなかった（最大 7.6pt）。
対策と現在の精度は D-012 と `docs/RESEARCH.md` §6 を参照。
Brotli(q=9, w=15) を代理に使う判断自体は維持（誤差の主因は代理圧縮器ではなくサンプル分散だった）。

---

## D-004: compact.exe の標準出力をパースしない

**判断**: 圧縮前後のサイズは `GetCompressedFileSizeW` で自前に測る。

**理由**（`docs/RESEARCH.md` §4）:
日本語環境では「データの圧縮率は 2.7 : 1 です。」と出る。
比率が「N : 1」形式である点も含め、出力に依存する実装は壊れる。

---

## D-005: 「圧縮済み」判定は物理/論理サイズ比で行う。ReparsePoint 属性は使わない

**判断**: `FolderProfile.AlreadyCompressedThreshold = 0.90`。物理/論理 < 0.90 なら圧縮済みとみなす。

**理由**（`docs/RESEARCH.md` §4）:
実測では、WOF 圧縮後も `FileAttributes.ReparsePoint` は立たなかった（6プロファイル全て 0 件）。
属性ベースの判定は誤りになる。

**注意**: reparse point の検査自体は、ジャンクション／シンボリックリンクの検出としては必要。
用途を混同しないこと。

---

## D-006: 見積もりのために試し圧縮しない

**判断**: `scan` はファイルへの一切の書き込みを行わない。

**理由**: 「解析するだけ」と説明したツールが不意にファイルを触るのが最悪の事故。
`LibraryScannerTests.走査は一切書き込みを行わない` で保証している。

---

## D-007: 削除したほうが得な場合はそれを言う。ただし削除は実行しない

**判断**: 長期未起動 × 大容量 × 圧縮が効かない、の組み合わせに
「削除すれば N GB 空きます（圧縮の約 M 倍）」という事実を添える。`--no-uninstall-advice` で無効化可能。

**理由**: ユーザーが欲しいのは空き容量であって、圧縮されたゲームではない。
「これは圧縮しても無駄です」と言えることが、見積もりの正直さの証明になる。

---

## D-008: スコアリングの主軸は「推定削減バイト数」。未起動期間ではない

**判断**: 候補順位は `容量 × (1 − 実測圧縮率)` を主軸に決める。
未起動期間は「圧縮状態が維持されやすいか」の補正として扱う。

**理由**（`docs/RESEARCH.md` §5）— これが最も重要な判断:

| タイトル | 容量 | 実測圧縮率 | 圧縮で空く量 |
|---|---|---|---|
| theHunterCotW | 116.5 GB | 29.4 % | **約 82 GB** |
| GTA V Enhanced | 96.1 GB | 99.5 % | **約 0.5 GB** |

容量はほぼ同じなのに、得られる結果が **160 倍**違う。
「未起動期間 65% / 容量 35%」のような、圧縮率を含まないスコアでは、
この2つがほぼ同順位で並ぶ。GTA V を上位に推したら、ユーザーは 96 GB を
何時間もかけて圧縮して 0.5 GB しか得られない。**一度やられたら二度と信用されない。**

「どのゲームを圧縮すべきかの判断支援」を製品の中心に据える以上、
**圧縮率がスコアの第一因子でなければ製品の主張が成立しない。**

---

## D-009: 判定ロジックは OS 非依存の Core に置く

**判断**: `SteamChecker.Core` は Windows API に直接依存しない。
`IFileSystem` 抽象と、アプリ層から注入するレジストリ参照デリゲートで分離する。

**理由**: WPF は Windows 専用。ロジックが WPF 側にあると Linux/CI でテストできない。
現在この分離のおかげで **Linux 上で 98 件のテストが全て通っている。**

---

## D-010: 初回リリースは Phase 0（読み取り専用）

**判断**: `compress` / `restore` は実装済み・実機検証済みだが、`--experimental` を必須にする。

**理由**: 機能不足ではなく範囲の選択。
初回は「解析だけするツール」として信頼を得ることを優先する。
無署名 EXE がゲームフォルダを再帰的に書き換える、という第一印象を避ける。

---

## D-011: 実測を省いてよいのは「圧縮フォーマットそのもの」だけ

**判断**: `FileCategory.Archive` を廃止し、二つに分割した。

| カテゴリ | 対象 | 扱い |
|---|---|---|
| `CompressionFormat` | `.zip .7z .rar .gz .bz2 .xz .zst .lz4` | 定義上すでに圧縮済み。**実測を省く** |
| `GameArchive` | `.arc .rpf .vpk .pck .forge .cab .msi` | 中身は不明。**必ず実測する** |

**この判断に至った経緯**（実機で発見したバグ）:

当初は `.arc` や `.rpf` を含む `Archive` カテゴリをまとめて実測対象から外し、
事前値 0.98（＝2%しか縮まない）で決め打っていた。コメントには
「明らかに縮まないカテゴリは実測せず事前値を使う（時間の無駄なので）」と書いてあった。

実機で 442GB のライブラリを scan したところ、theHunter: Call of the Wild について

```
117 GB / 圧縮見込み 2.38 GB
· 実測したところ 2 % しか縮みません
```

と表示された。しかし同じゲームの `.arc` を `compact.exe /EXE:LZX` で実際に圧縮すると
**29.4%**（`docs/RESEARCH.md` §1）。実際には **約 82 GB** 削減できる。

**34 倍の過小評価**であり、しかも「実測したところ」と表示していた。実測していないのに。

**根本原因**: `docs/RESEARCH.md` §4 に「実ゲームの拡張子は独自形式が支配的であり、
拡張子ベースの推定は当たらない」と自分で書いておきながら、
高速化のために拡張子ベースの決め打ちを再導入していた。
`FileCategory.cs` のコメントには `.pak / .dat / .bin` について
「拡張子だけでは判断できないので Unknown に落として実測に委ねる」と書いてあり、
同じ性質の `.arc / .rpf` を逆の扱いにしていた。設計内部の矛盾。

**教訓**: 「明らかに」で始まる最適化のコメントは疑う。
このツールの前提は「拡張子では分からないから実測する」であり、
その前提を破る最適化は、製品の主張そのものを壊す。

**回帰テスト**: `EstimatorTests.ゲーム独自コンテナは名前がアーカイブでも必ず実測する`

## D-012: サンプル予算はフォルダサイズに比例させる（固定 64MB は精度不足）

**判断**: `SamplingOptions` を「論理サイズの約 6%（`AdaptiveBudgetDivisor=16`）、
下限 64MB・上限 1GB」の適応予算に変更。あわせて 1 ファイルあたり最大 16MB、
カテゴリあたり最大 256 ファイル、大ファイルのスライス読みを 3 箇所 → 8 箇所に変更。

**経緯**（2026-07-30、`docs/RESEARCH.md` §6）:
D-003 の校正（誤差 2.05pt）は単一拡張子の等質プロファイル 4 本に対するもので、
実タイトルの異種混合フォルダには一般化しなかった。5 タイトルの層化複製に対する
実測では、旧既定（64MB 固定）の誤差は最大 **+7.6pt**（平均 4.1pt）。
サンプル量を 2GB まで増やすと全タイトル 3pt 以内に収束したため、
誤差の主因はアルゴリズムではなくサンプル分散と特定した。

**採用しなかった案**: ファイル論理サイズによる加重合成。
理論上は正しいが、既定予算では少数の巨大ファイルの個体差が全体を支配し、
誤差が最大 +8.8pt へむしろ悪化した（同 §6）。等重み平均は偏りはあるが分散が小さい。

**残る限界**: 新既定でも誤差は最大 +5.7pt（平均 2.7pt、5 本中 3 本が 3pt 以内）。
「±数ポイントぶれる推定値」として表示すること。3pt を全タイトルで保証する水準には
達していない。

**2026-07-30 追補（v3）**: 実ゲーム（Slots & Daggers）の全量圧縮で +10.6pt の
破綻を発見。原因は深掘り優先の選択がカテゴリ内の非圧縮性グループ（.bank 42MB）を
取りこぼしたこと。対策として (1) 2 段階選択（広く浅く→深く）、(2) カテゴリ内の
拡張子層化（拡張子間は正確なバイト比で合成）を導入。正確な正解に対する誤差は
最大 4.0pt に改善（`docs/RESEARCH.md` §6）。公称精度は「±6pt 程度」を維持。

## D-013: 書き込みを伴う操作の直前検査は fail-closed

**判断**: `PreFlightChecker` を新設し、compress / restore の直前に必ず通す。
判定できないもの（ファイルシステム不明・プロセス一覧が取れない・空き容量不明）は
すべて「安全でない」と扱い実行を止める。

**理由**: scan の NTFS 判定は fail-open（判定不能を NTFS とみなす）にしている。
読むだけなら誤検出の害が小さいから。書き込みでは逆で、誤って進めた場合の害が
取り返しにくい。同じ判定でも読み書きで倒す方向を変える。

**検査項目**: ライブラリ配下か（installdir のサニタイズ含む）/ manifest の現存（TOCTOU）/
NTFS / 親子階層の reparse point / Steam クライアント起動中 / ゲーム exe 使用中 /
DirectStorage 兆候（これのみ Warn）/ 容量測定可否 / 空き容量。

**あわせて修正した実バグ**（2026-07-30 の独立レビューで発見）:
- `installdir` に `..` や絶対パスを含む manifest がそのまま `FullPath` になっていた
  （パストラバーサル）。`SteamReader` 側でも読み込み時に拒否するようにした
- `StateFlags` が未完了でも理由コードを積むだけで「圧縮推奨」まで素通りしていた。
  `Advisor` で `DoNotCompress` を即返すよう修正
- `AdviceFormatter` が `Estimate.Measured=false` でも「実測したところ」と表示していた
  （D-011 と同種の虚偽表示）。分岐を追加
- キャンセル時に compact.exe を kill せず放置していた。プロセスツリーごと停止するよう修正
- `restore --all` がジャーナル記載の任意パスを無検査で処理していた。
  検出済みライブラリの common 配下のみに制限

## D-014: GUI からの圧縮実行も CLI と同一のゲートに揃える

**判断**: WPF に圧縮・復元の実行を配線する。ただしゲートは CLI の `--experimental` と
完全に同等にする — (1) 既定オフの明示的オプトイン（チェックボックス または `--experimental` 引数）、
(2) 実行直前に manifest を読み直して `PreFlightChecker`（fail-closed）、
(3) サイズと削減見込みを提示した確認ダイアログ、(4) 進捗表示と中断ボタン、
(5) `OperationJournal` への記録。

**理由**: 製品の最終形は「GUI でリストを見て、そこから圧縮まで実行できる」こと。
表示だけの GUI は道半ばで、CLI にしか書き込み経路がないのは段階分け（D-010）の
一時状態にすぎない。一方で GUI は CLI より誤操作しやすいため、
ゲートを CLI より緩くしない。判定・検査・実行は全て Core を呼ぶだけにし、
WPF 側にはオーケストレーションと文言表示以外を書かない（D-009 維持）。

**初回リリース（Phase 0）の扱い**: オプトインが既定オフである限り
「解析だけするツール」という第一印象は守られる。D-010 は変更しない。

**2026-07-31 追記**: この GUI のオプトイン（チェックボックス）は D-015 で廃止した。

---

## D-015: GUI の「圧縮機能を有効にする」チェックボックスを廃止する

**判断**: WPF から実験的機能のオプトイン UI を削除し、
タイトルを選択すれば直接「圧縮...」「元に戻す...」を実行できるようにする。
CLI の `--experimental` は維持する（コマンドラインは誤爆の質が違う）。

**理由**（ユーザーからの指摘、2026-07-31）:

> 「そもそもこのソフトは圧縮するためのソフトだから、
>   どういう意図があって、この機能があるかわかりにくい」

その通りだった。あのチェックボックスは D-010 の「無署名 EXE がいきなり
ゲームフォルダを書き換える第一印象を避けたい」という**開発者の不安が
UI に漏れ出したもの**で、ユーザーの語彙では意味をなさない。

さらに悪いことに、**あれは実際には何も守っていなかった**。
書き込みの安全性を担保しているのは以下の 4 つで、いずれも常時有効:

1. `PreFlightChecker`（fail-closed。Steam 起動中・非 NTFS・reparse point 等を拒否）
2. サイズと削減見込みを提示する確認ダイアログ
3. `OperationJournal` への記録
4. ワンクリックの復元

**守っていないものを守っているように見せる UI は、安全ではなく安全の演出であり、
かえって有害**（ユーザーが「チェックを入れた＝危険を承知した」と錯覚し、
本当の警告である確認ダイアログを読み飛ばす）。

**代わりにやったこと**: 画面下部の常設注記に
「いつでも解除できる / 更新で自動解除される / 実行前に Steam の起動状態を確認する」
を明記し、安全の根拠を画面上で説明する形にした。
